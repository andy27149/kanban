# 上下游结算看板设计（条目 7-9）

## 背景

《看板调整建议0825.docx》条目 7-9 要求新增三个业务模块，数据来自 `上下游结算.xlsx`（用户已确认：**仅结构模板，数值是占位数据，非真实业务数据**，真实文件将来会以相同结构替换）：

| 条目 | 名称 | 来源 sheet | 原文诉求 |
|---|---|---|---|
| 7 | 采购管理表 | 上游结算 | 统计维度以合同为单位，统计合同数量、实发数量、煤款和运费的应付未付及应退金额等信息，根据不同状态展示合同进度 |
| 8 | 订单管理表 | 下游订单管理 | 以链条和合同为维度，展示基础数据。提取提醒数据，已经装运船、待装船。订单状态可筛查 |
| 9 | 销售管理表 | 下游结算 | 以链条和合同为维度，展示基础数据。提取提醒数据，项目款项应回款金额、已经回款金额、应回款金额，根据不同状态展示合同进度 |

已与用户逐项确认的决策：

1. **数据真实性**：仅结构模板，值可能是空/占位。设计必须容忍字段当前为空，且在真实数据填入后自动生效，不需要改代码。
2. **页面结构**：不新建页面/Tab，在现有单页看板下方新增独立表格卡片（同 `同一页面新增表格区块` 决策）。
3. **应付/未付/应退等字段**：直接读取 Excel 里已填的值，不做系统侧计算或推导。
4. **"提取提醒数据"的形式**：两者都要——状态统计（可视化/徽章）+ 状态筛选/高亮，二者用同一组交互组件（可点击状态徽章）实现。
5. **图表**：6 个（4 个可立即用样本数据验证 + 2 个当前无数据但结构已备好，无数据时显示提示而非空图）。

## 架构约束（继承自现有系统，条目 7-9 必须遵守）

`scripts/export_static.py` 会把 `data.json` 整体内嵌进离线单文件 HTML（`exports/经营看板.html`），运行时零服务端依赖。因此：

- 所有新增数据（表格行、图表聚合、状态统计）**必须在 `/upload` 时由 `build_dashboard_data` 一次性算完**，写入 `data.json`。
- 前端 `dashboard.js` 只做纯客户端渲染/筛选/高亮，**不新增 Flask 路由**。
- 上传流程本身不需要改动：`/upload` 已通过 `request.files.getlist("files")` 支持多文件，只要把 `上下游结算.xlsx` 和 `基础表.xlsx` 一起上传，`config.yaml` 按 `source_file` 匹配即可。

## 新增共享读取函数：`_read_sheet_rows`

三张新 sheet 的共同结构问题：**第 1 行是标题**（如"采购管理表"），**第 2 行才是真实表头**；且"上游结算"表的"已付金额/未付金额/应退金额"因为煤款和运费各一套，**列名重复出现两次**。

现有 `_read_dataframe`（`extractor.py`）用 `pd.ExcelFile.parse()`，默认把第 1 行当表头，且 pandas 会给重复列名自动加后缀（如 `已付金额.1`），两者都不适用。为此新增一个不依赖 pandas、直接用 openpyxl 按行读取的函数：

```python
def _read_sheet_rows(uploads_dir, source_file, sheet_name, header_row, id_column):
    """
    header_row: 表头所在的 Excel 行号（1-indexed），数据从 header_row+1 开始。
    id_column: 表头文本，用于定位"合同编号"列的位置；该列为空的行（标题行残留/合计行/空行）自动跳过。
    返回 (columns: list[str], rows: list[list])，columns 保留原始表头文本，允许重复。
    """
```

实现方式：openpyxl 读取 `header_row` 那一行所有单元格文本作为 `columns`（重复的列名原样保留，因为这里只是展示/按位置取值，不依赖列名唯一性）；从 `header_row+1` 到该 sheet 最后一行，逐行读值，找到 `id_column` 第一次出现的位置，跳过该位置为空的行；其余单元格值用现有 `_clean_value` 做类型清洗（日期格式化等）。

此函数只服务于 `上下游结算.xlsx` 的三张新 sheet；`基础表.xlsx` 相关的现有 `_read_dataframe`/`fixed_range` 逻辑不受影响、不做修改。

## 新增表格模式：`sheet_table`

`extract_table` 新增一个 mode 分支，直接调用 `_read_sheet_rows` 把整表原样展示（用户已确认"直接读取表格填写值，不做计算"）：

```yaml
mode: sheet_table
source_file: "上下游结算.xlsx"
sheet: "上游结算"
header_row: 2
id_column: "合同编号"
status_column: "进度"      # 用于前端状态徽章 + 筛选，见下
show_totals: true          # 仅采购管理表设为 true，见"合计行"一节
```

返回结构在现有 table 对象基础上透传 `status_column`（和可选的 `totals` 行数组），前端据此渲染徽章/筛选/合计行，Python 侧不做状态分类或语义判断。

### 采购管理表的合计行（仅此表，对应条目 7"统计...数量/金额"）

`show_totals: true` 时，在 `_read_sheet_rows` 过滤后的行基础上额外算一行 `totals`：
- `id_column` 所在列：显示 `"合计（{n} 份合同）"`（n = 有效行数）
- 其余列：若该列所有非空值均为数字，则求和；否则留空（不猜测非数值列的合计语义）

`totals` 作为表格对象的独立字段（不混入 `rows`），前端渲染成表尾加粗行。订单管理表、销售管理表不设置 `show_totals`（原文没有"统计"措辞，避免过度设计）。

### 三张表的具体配置

| key | title | sheet | id_column | status_column | show_totals |
|---|---|---|---|---|---|
| purchase_contracts | 采购管理表 | 上游结算 | 合同编号 | 进度 | true |
| order_management | 订单管理表 | 下游订单管理 | 合同编号 | 状态 | false |
| sales_contracts | 销售管理表 | 下游结算 | 合同编号 | 状态 | false |

标题直接取 sheet 自带的标题文本（三个 sheet 的第 1 行本身就是"采购管理表/订单管理表/销售管理表"），与反馈条目原文命名一致。三张表各自独立（不设 `view_group`），作为三个新的表格卡片依次追加在现有表格区域下方。

## 状态徽章：统计 + 筛选二合一

对话中确认"提取提醒数据"要同时有统计和筛选能力。设计为一组可点击徽章，而不是徽章+下拉框两套 UI：

- 前端（`dashboard.js`）拿到 `table.status_column` 后，在 `table.columns` 里定位该列下标，遍历 `table.rows` 统计每个状态值出现次数，渲染成徽章（如"待装船（3）"）
- 点击某徽章：表格只显示该状态的行，徽章高亮为选中态；再点一次或点"全部"恢复显示所有行
- 这是纯客户端逻辑，状态徽章的分组**完全按 Excel 里出现的原始文本**统计，不做"已完成/进行中"之类的语义归类（样例状态文案本身不统一，如"结项""下游清算完成""发票尾款待回"，系统不替业务发明分类）
- 三张新表共用同一段渲染代码（写一次，`status_column` 存在就启用）

## 图表设计

### 4 个立即可用的图表（复用现有 `x`/`y` 或 `x`/`series` 渲染，`dashboard.js` 零改动）

新增图表聚合 mode `group_by`（用 `_read_sheet_rows` 读数据后在 Python 里用字典聚合，不引入 pandas groupby）：

```yaml
mode: group_by
agg: sum   # 或 count
source_file: "上下游结算.xlsx"
sheet: "上游结算"
header_row: 2
id_column: "合同编号"
group_column: "矿区"
value_column: "结算数量"   # agg: count 时不需要此字段
```

| key | type | title | sheet | agg | group_column | value_column |
|---|---|---|---|---|---|---|
| purchase_volume_by_region | bar | 采购按矿区汇总实发数量（吨） | 上游结算 | sum | 矿区 | 结算数量 |
| purchase_progress_distribution | pie | 采购合同进度分布 | 上游结算 | count | 进度 | — |
| order_status_distribution | pie | 订单状态分布 | 下游订单管理 | count | 状态 | — |
| sales_status_distribution | pie | 销售合同状态分布 | 下游结算 | count | 状态 | — |

聚合结果直接产出 `{x: [...], y: [...]}`，与现有 `buildChartOption` 消费的数据形状完全一致。

### 2 个使用绝对区域求和的图表（结构已备好，通用降级逻辑兜底空值）

复用 KPI 已有的"整段单元格区域求和"能力（`_read_fixed_range_values` + 求和），只是把结果拆成几根柱子而不是一个数。新增图表 mode `sum_bars`：

```yaml
mode: sum_bars
source_file: "上下游结算.xlsx"
sheet: "上游结算"
x: ["已付金额", "未付金额", "应退金额"]
series:
  - name: "煤款"
    ranges: ["K3:K12", "L3:L12", "M3:M12"]
  - name: "运费"
    ranges: ["P3:P12", "Q3:Q12", "R3:R12"]
```

| key | type | title | sheet | x | series/ranges |
|---|---|---|---|---|---|
| purchase_payment_status | bar | 采购煤款/运费收付情况（元） | 上游结算 | 已付金额/未付金额/应退金额 | 煤款: K3:K12,L3:L12,M3:M12；运费: P3:P12,Q3:Q12,R3:R12 |
| sales_collection_status | bar | 销售回款情况（元） | 下游结算 | 结算金额合计/已回金额合计/待回金额合计 | 单系列: O3:O21,T3:T21,U3:U21 |

### 通用"暂无数据"降级（唯一的前端改动）

`build_dashboard_data` 对**所有**图表（不限于上述 2 个）做一次通用检查：聚合结果的所有数值若全部是 `0` 或 `None`，则不返回 `x`/`y`/`series`，改为：

```json
{"key": "...", "title": "...", "hint": "该图表依赖尚未回填的业务字段，暂无数据"}
```

`dashboard.js` 的 `renderCharts` 增加判断：`chart.hint` 存在且无 `chart.error` 时，渲染一个新样式 `.chart-hint`（语气比现有报错用的 `.chart-error` 更中性，如"暂无数据"提示框），不初始化 echarts 实例。这个降级逻辑是通用的，不针对特定图表硬编码——真实数据填入后数值不再全零，自动恢复正常图表，不需要改代码或配置。

**重新核验样本数据后的修正（第二轮，连同 R 列逐格复查）**：`sales_collection_status`（销售回款情况）的"结算金额"列（O3:O21）在样本文件里**已有真实非零值**，只有"回款合计"（T列）和"待回金额"（U列）为空——不会触发全零判定，按通用降级逻辑正常渲染成 3 根柱子（结算金额有真实高度，另外两根为 0）。

`purchase_payment_status`（煤款/运费收付情况）的"煤款"子系列（K3:K12/L3:L12/M3:M12）确认全部为空。但"运费"子系列的应退金额列（R3:R12）**并非全部为空**：第 4 行是数值 `14000`，其余 9 行是文本"无"（非数字，求和时按 `sum_bars` 的既定规则被跳过、不计入合计），已付/未付（P/Q 列）确认全部为空。也就是说这 6 个绝对区域里有一格带真实数值——"运费"这一子系列会是 `[0, 0, 14000]`，不是全零。因为 `_chart_is_empty` 对多系列图表要求**所有**子系列都全零/空才判定为空，"煤款"子系列全零但"运费"子系列不是，整张图不会触发 hint 判定。

结论：在当前样本数据下，`purchase_payment_status` 和 `sales_collection_status` **都不会**走 `hint` 分支——两者都会渲染成正常图表（前者是"煤款 3 根柱子全 0 + 运费应退单独一根 14000"，后者是"结算金额一根有真实高度 + 另外两根 0"）。通用降级逻辑本身没有问题、按设计保留（用于将来真正全空的字段/图表），这里只是更正此前两轮对"这两个图表在样本数据下会触发 hint"的不准确描述，不需要改动任何代码或架构，也不需要为这一格孤立数值增加特殊处理。

## 数据流与错误处理

沿用现有约定：单个表/图表出错时该条目返回 `{key, title, error: "..."}`，前端已有的 `.table-error`/`.chart-error` 渲染路径直接复用，不影响页面其余部分：

- sheet 不存在（如用户没上传 `上下游结算.xlsx`）→ 该 table/chart 走 error 分支，其余基础表相关内容不受影响
- `id_column`/`status_column`/`group_column` 在表头行里找不到 → 视为配置错误，返回 `error`，不静默跳过

## 关键假设与风险（因源文件是结构模板而非真实数据，显式记录）

- 假设真实文件的列名、列顺序、sheet 名与本模板一致；若有出入，只需改 `config.yaml` 的 `header_row`/`id_column`/`group_column`/range 等配置，不需要改代码。
- 状态徽章按 Excel 原始文本分组，不做业务语义归类；如果真实数据的状态文案比样本更混乱（比如同一状态有多种写法），徽章会拆成多个条目，这是已知的、故意不处理的行为（避免系统替业务发明分类规则）。
- "上游结算"表已付/未付/应退列重复出现（煤款/运费各一套）——`sheet_table` 展示模式下这不是问题（原样显示两次相同列名即可），但 `sum_bars` 图表用的是**绝对单元格区域**而非列名匹配，一旦真实文件插入/删除列导致这些字段挪位，需要同步更新 `config.yaml` 里的 range，这是选用"按位置取值"方式的已知代价（换来的好处是彻底避免了列名重复的歧义）。
- 6 个图表 + 3 个表格全部不新增 Flask 路由，不影响 `scripts/export_static.py` 现有的离线导出机制。
