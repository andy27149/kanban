# Boss Dashboard 可展示内容计划（基于真实基础表重新分析）

> 背景：此前 config.yaml/spec 的内容（总营收/总利润/库存台账/销售明细等）是凭空杜撰的，不对应任何真实文件。用户唯一提供的真实数据源是 `docs/superpowers/基础表.xlsx`。本文档基于对该文件的逐表分析重写，所有条目均标注可追溯的 sheet/cell 出处。实施前需用户确认。

## 一、数据源结构（唯一真实文件：基础表.xlsx，13 个 sheet）

业务是煤炭贸易物流：多个矿区/来源的煤炭通过铁路或汽运入库到港口（锦州港），检测质量指标后堆存，再按订单配煤装船出库。

| Sheet | 作用 | 结构要点 |
|---|---|---|
| `合计` | 品类级汇总：入库/出库/倒运亏/库存余额/实际库存 | 2 行合并表头（row4+row5），11 个品类各一行 + 合计行 |
| `出库明细` | 出库船次流水 | 3 行合并表头（row5-7），15 条真实出库记录 + 按矿区汇总区块（row27-38） |
| `4-5月C` `6月C` `4-6月B` `4月A` `5-6月A2` `6月B2` `8月A3` | 铁路批次入库明细（7 张，按矿区/批次/月份分组） | 2 行合并表头，含热值/硫分/灰分等质量数据 |
| `6-7月H` `7月T` `7月M` | 汽运入库明细（3 张） | 2 行合并表头，含 SGS/中检报告编号 |
| `F` | 世德物产托盘入库明细 | 2 行合并表头 |

**已核实的数据一致性**（证明 `合计` 表确实是其余 12 张明细表的真实汇总，而非独立编造）：
- `5-6月A2` 表最后一行"标重"合计 = 205,312 吨，与 `合计` 表 A2 行"入库合计"205,312 完全一致；"轨道衡"合计 203,426.87 同样一致。
- `F` 表 FB 品类两行"过磅"合计 = 6,637.88，FA 品类两行合计 = 45,596.44，分别与 `合计` 表 FB/FA 两行"入库合计"完全一致。

## 二、建议展示内容（v1，均可追溯到具体 sheet/cell）

### KPI 卡片（来源：`合计` sheet 第 17 行合计行）
1. 入库总量：728,528.02 吨
2. 出库总量：602,420 吨
3. 库存余额合计：125,757.86 吨
4. 锦州港实际库存合计：123,766.25 吨
5. 倒运亏合计：350.16 吨（目前仅 B 品类有倒运亏）

### 图表
1. **按品类对比入库 vs 出库**（分组柱状图）— 来源 `合计` 第 6-16 行，x=品类，y=入库合计 & 出库合计
2. **库存余额分布**（柱状图/饼图）— 来源 `合计` 第 6-16 行 K 列（库存余额）
3. **出库船次装货量趋势**（折线图/柱状图）— 来源 `出库明细` 第 8-22 行，x=完货时间，y=装货港称重

### 表格
1. **品类汇总表** — 直接转录 `合计` sheet：品类/权属/入库合计/出库合计/倒运亏/库存余额/实际库存
2. **出库明细表** — `出库明细` 第 8-22 行：完货时间/船名/航次/装货港/装货港称重/目的港/目的港称重/发货人/收货人
3. **出库按矿区汇总** — `出库明细` 第 27-38 行（表内已有现成汇总，无需重新计算）

### 暂不纳入 v1（标记"待验证"，非直接拒绝）
- **11 张入库明细表的逐批次/逐车厢原始数据**（热值/硫分/灰分等质量指标）：颗粒度是运营层面的，不适合一屏老板看板；且铁路 vs 汽运两类表结构不同（字段不完全一致），统一处理需要额外设计。如后续有人反馈需要"质量数据钻取"再单独做。
- **按收货人汇总出库量**：`出库明细` 里"出库数量"分散在多个品类列中，需要先确认统计口径（是否等同于 `合计` 表口径）才能做汇总，先列为待确认项。

## 三、需要用户确认的问题

1. 上述 KPI/图表/表格范围是否覆盖你想在看板上看到的内容？是否有遗漏（比如你更关心质量指标、还是更关心资金/成本，而基础表里目前没有任何金额/成本字段）？
2. 品类代码（C/B/A/A2/B2/H/T/M/F 等）与矿山全称的对应关系，我从各入库表标题推测为：C=乌珠穆沁，B=沙尔塔拉，A/A2=贺斯格乌拉（含北化批次），H=乌煤，T=大唐矿，M=西三矿，F=世德物产。是否准确？看板上是否需要显示全称而非代码？
3. "倒运亏"和"锦州港实际库存 vs 库存余额"之间的差异，是需要重点预警的异常，还是正常业务波动？是否需要在 UI 上高亮？
4. 这份 `基础表.xlsx` 的更新节奏是怎样的（每天/每周/每航次）？决定了以后上传流程是整份表覆盖替换，还是需要支持增量追加历史数据。

## 四、对现有实现的影响（供确认后实施参考，暂不动工）

- `config.yaml` 需要改为引用单一文件 `基础表.xlsx` 的多个 sheet，而不是三个虚构文件。
- `合计`/`出库明细` 两个 sheet 均为多行合并表头，现有 `extractor.py` 的 `header_match` 模式假设单行表头、按列名文本查找——需要新增一种"已知固定行列范围，直接读取矩形区域"的抽取模式（可以在现有 `fixed_range` 基础上扩展成读取多行多列，而不仅是单个格子）。
- 已提交的 `docs/superpowers/specs/2026-08-20-boss-dashboard-design.md` 描述的是虚构模型，需要在这份计划确认后一并更正或废弃。
